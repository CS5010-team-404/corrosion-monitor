# NIST SP 800-53 Rev. 5: mapping of selected controls

Corrosion Watch is **aligned with selected controls; it is not certified or assessed**. This page maps the controls
we could check against the code to what the code actually does, with the file or class that does it. Status is
**Implemented** (the control's core is in the code and tested), **Partial** (some of it is, the gaps are listed) or
**Planned** (not done). Hosting (Render, Aiven) provides some protections the code relies on; those are named as such
and were not verified beyond the repository's configuration. Short paths: `B` = `backend/src/main/java/com/team404/corrosion`,
`P` = `platform`. Checked against `dev` on 2026-11-22.

| Control | Status | What the code does | Gaps |
|---|---|---|---|
| **AC-2** Account management | Partial | Accounts in `app_user` (V1; role CHECK in V2; `enabled`, `last_login_at` in V9). Admins list users, unlock them and change roles (`B/auth/admin/UserAdminController`, `UserAdminService`), each audited (`ACCOUNT_UNLOCKED`, `USER_ROLE_CHANGED`); the last enabled admin cannot be removed and admins cannot demote themselves (`UserAdminRules`). Disabled accounts cannot sign in (`AuthService.login`). | No API to create, disable or delete accounts (the four demo accounts come from `B/auth/DemoUsers`, all with one password from `ECP_DEMO_PASSWORD`); no expiry for inactive accounts; a role change or disable applies only when the 8-hour token expires (no revocation). |
| **AC-3** Access enforcement | Implemented | Deny by default: `B/web/SecurityConfig` (`/api/v1/admin/**` ADMIN; reports and audit MANAGER/ADMIN; alert actions TECHNICIAN/ADMIN; other `/api/v1/**` signed in; `anyRequest().denyAll()`). Extra checks in controllers: `AuditController` (verify and checkpoints), `ProfileController` (PUT is ADMIN-only, refusals audited as `ACCESS_DENIED`). The platform follows the same pattern (`P/ecp-platform-app/.../config/SecurityConfig`), with device ingestion authenticated by HMAC instead of JWT. | `ecp.platform.auth=none` turns platform checks off (local development only; `docker-compose.platform.yml`). `/ws/**` is open on both services by design (change notices only, client messages dropped). |
| **AC-6** Least privilege | Partial | Four roles with separate rights; the operator role is read-only. Both Docker images run as a non-root user (`deploy/platform.Dockerfile`, `backend/Dockerfile`: `USER app`, uid 10001). Actuator exposes only `health` (backend) and `health,info` (platform). | One database account runs the applications and the migrations, so it could also drop the audit triggers; the `REVOKE` for `audit_log` in `V1__team_schema.sql` is only a comment. |
| **AC-7** Unsuccessful logon attempts | Implemented | `B/auth/LoginPolicy`: 5 failures lock the account for 15 minutes (`MAX_FAILURES`, `LOCK_DURATION`); while locked even the right password is refused (HTTP 423); success resets the count. Unknown e-mails get the same answer with equalised timing. Failures and locks are audited; admins can unlock. Covered by `LoginPolicyTest` and `AuthControllerTest`. | No rate limiting by client address. |
| **AU-2** Event logging | Implemented | Security-relevant events go to `audit_outbox` in the same transaction as the change: sign-in, failure, lock (`B/auth/LoginAudit`); unlock and role change; alert lifecycle and corrective actions (`B/alert/OutboxAlertEvents`); profile changes; audit verification and refused audit access (`B/audit/AuditService`); sensor registration, key rotation, interval change, simulator scenario, health issues and service outages (`P/ecp-common/.../audit/JdbcAuditRecorder`). | Requests refused by the security filter (401/403) are not audited; device rejections are kept in `ingest_rejections`, not the audit chain; no sign-out event (tokens are stateless). |
| **AU-3** Content of audit records | Partial | `audit_log` (V4): time of the event and of recording (UTC), actor type (user, system, device), actor, action, entity type and id, details (JSON, with old and new values for changes), previous and own hash. | No source address or client details (the V1 `source_ip` column did not survive the V4 redesign); outcome is part of the action name rather than a field. |
| **AU-6** Audit review, analysis and reporting | Partial | `GET /api/v1/audit` with filters (actor, action, entity, time) and paging, and the Audit page in the UI, for managers and admins; on-demand chain verification with stored results. | Review is manual: no automatic analysis or alerting on audit patterns (for example many failed sign-ins). |
| **AU-9** Protection of audit information | Partial | Tamper-evident: `audit_log` is append-only (triggers `audit_log_no_update` / `audit_log_no_delete` in `V4__audit_chain.sql` raise an error); each entry carries a SHA-256 hash over its fields and the previous hash (`B/audit/HashChain`); `ChainVerifier.verifyAgainstHead` detects edits, gaps and cut-off entries against `audit_chain_head` and daily checkpoints. A single writer (`AuditChainWorker`). Read access is limited to managers and admins. | Checkpoints live in the same database (a copy the application cannot write is planned, `docs/GAPS.md`); the hashes are not keyed, so someone with full database write access could rebuild the whole chain; the outbox has no triggers. |
| **AU-10** Non-repudiation | Partial | Every user action is attributed to the signed-in user (JWT subject) in the hash-chained log; device readings are tied to a device key by HMAC. | No digital signatures: JWTs and device signatures use shared secrets, so they authenticate but do not prove origin to a third party; the demo accounts share one password. |
| **IA-2** Identification and authentication (users) | Partial | Each user signs in with e-mail and password (`POST /api/v1/auth/login`) and gets a JWT (HS256, 8 hours, `B/auth/TokenService`) that both services check; no basic or form login. | No multi-factor authentication, single sign-on, refresh or revocation. |
| **IA-5** Authenticator management | Partial | Passwords stored with BCrypt (`B/auth/PasswordConfig`); no built-in default password (`DemoUsers` seeds nothing without `ECP_DEMO_PASSWORD`). The backend refuses to start with a JWT secret under 32 bytes (`JwtKeys.MIN_BYTES`). Device keys are 256-bit random, shown once, stored encrypted, and can be rotated (`SensorSecretCipher`, `DeviceController.rotate`). | No password length or complexity rule, no change or reset flow, no expiry or history. The platform's `application.yml` has development fallbacks for the JWT secret and the key-encryption key, which a deployment must override (Render does). |
| **SC-8** Transmission confidentiality and integrity | Partial | Device requests are integrity-protected: HMAC-SHA256 over timestamp and body, checked in constant time (`P/ecp-common/.../domain/Hmac`), within a ±5-minute window; readings are stored once per sequence number. HTTPS in production is provided by Render; the database connection requires TLS in the documented production URL (`render.yaml`, `sslMode=REQUIRED`). | TLS is not enforced by the code itself (no HSTS or channel security; local defaults use plain HTTP and `useSSL=false`). A replayed device request inside the window is answered 202 without storing anything new; rejecting it outright is in review (replay protection PR). |
| **SC-12** Key establishment and management | Partial | Production secrets come from the environment: Render generates the JWT secret and the key-encryption key (`generateValue` in `render.yaml`); device keys are generated by the server, rotated on demand and audited (`SENSOR_SECRET_ROTATED`). | One symmetric JWT key shared by both services, with no key id or rotation procedure (rotating signs everyone out); no rotation or re-encryption for the key-encryption key; no KMS or HSM. |
| **SC-13** Cryptographic protection | Implemented | Standard algorithms from the JDK and Spring Security only: HS256 for tokens, BCrypt for passwords, HMAC-SHA256 for device requests, SHA-256 for the audit chain, AES-256-GCM (`Encryptors.delux`) for device keys at rest. | Nothing is FIPS-validated or configured for FIPS. |
| **SI-4** System monitoring | Implemented | Sensor health every 5 s (`P/ecp-health`: offline, stuck, impossible, erratic, lossy, bad signatures, clock skew), with alerts and audit entries; every rejected device request is kept with its reason (`ingest_rejections`); the service watchdog raises `SERVICE_DOWN` when a background job stops (`ServiceWatchdog`); health endpoints for the hosting platform. A check of the rules on real faulty sensor data is in review (Intel Berkeley Lab replay PR). | Monitoring covers the sensors and services, not user-side intrusion (no detection of sign-in bursts, no IDS). |
| **CM-3** Configuration change control | Implemented | Schema changes only through Flyway migrations (backend V1–V9, platform migrations with their own history); applied migrations are protected by `MigrationChecksumTest` against `applied-migrations.txt`. Every change goes through a pull request into `dev` with review and CI (`.github/workflows/ci.yml`, `platform.yml`, `frontend.yml`), following `CONTRIBUTING.md` and the PR template. | Branch protection is not enforced by GitHub on our plan (the team enforces it by agreement); there is no checksum test for the platform's migrations; `applied-migrations.txt` lists V1–V8. |

**Out of scope here:** physical and environmental controls, contingency planning, incident response, personnel
security and supply-chain controls. They depend on the organisation that would run the system, not on this code.
